# Audit de sécurité, confidentialité et préparation RGPD

**Date : 10 novembre 2026. Périmètre : agemocratie_final_cloudflare, version à publier, comparée au commit 8797dc7.**

## Verdict

**Ne pas publier cette version comme un vote à anonymat garanti, ni la déclarer conforme au RGPD en l’état.** Les tests fonctionnels précédents vérifiaient le fonctionnement, pas une garantie d’anonymat ou l’absence de vulnérabilités dans les dépendances. Le qualificatif précédent de « prêt » doit être limité au fonctionnement observé ; l’audit révèle des blocages supplémentaires.

Le retrait du code d’AG des mails est utile. Il ne rend pas le vote cryptographiquement anonyme : le serveur reçoit le choix en clair et les changements de plusieurs tables peuvent être rapprochés dans le temps. L’administrateur du site (compte applicatif), l’administrateur Cloudflare/D1 et le gestionnaire des OTP n’ont pas les mêmes pouvoirs ; les risques ci-dessous précisent les accès nécessaires.

Aucune modification des mécanismes de vote, des dépendances, de la base distante ou des comptes n’a été faite pendant cet audit. Seuls le `.gitignore`, les documents et les preuves locales ont été ajoutés ou renforcés. Aucun vrai mail envoyé pendant les preuves.

## Méthode et limites

Lecture du Worker, des modèles, des migrations 002–006, du relais Gmail, des configurations et du verrou uv. Exécution de huit scénarios bornés sur une base SQLite temporaire avec le vrai routage FastAPI et un envoi simulé, à partir de la fixture des tests existants. Consultation des avis de sécurité des mainteneurs, de la documentation D1 et des sources officielles RGPD. Recherche de correspondances exactes des secrets actuellement connus dans les objets accessibles de l’historique Git local.

Pas d’accès au tableau de bord Cloudflare, pas d’inspection de D1 de production, des journaux réels, des réglages de région, du compte Google, des contrats, des droits des collaborateurs ou des branches absentes du clone. Ce n’est ni un pentest externe exhaustif ni une certification. Les résultats sont conditionnés aux configurations décrites.

Pour reproduire les preuves sans production, dans un environnement Python comportant les dépendances de développement et httpx :

```powershell
python audit_securite/verifications.py
```

**Huit tests « OK » signifie ici que les huit limites ont été reproduites, pas qu’elles sont corrigées.**

## Constats prioritaires

### S01 — Élevé : dépendance Starlette vulnérable ; parsing de formulaires non borné

Preuves : `cloudflare/uv.lock` verrouille Starlette **0.52.1**. `cloudflare/pyproject.toml` impose `<1`. Les routes commencent souvent par `await request.form()` avant la validation CSRF, notamment `worker.py:733` et `email_access.py:114`. L’audit OSV de 25 versions a remonté cinq avis distincts, avec leurs alias :

| Avis | Sujet | Version corrigée annoncée | Applicabilité observée |
|---|---|---|---|
| GHSA-82w8-qh3p-5jfq / CVE-2026-54283 | Limites `request.form()` ignorées pour URL-encoded, DoS | 1.3.1 | Pertinent : ces formulaires sont utilisés ; défaut de limite reproduit sur une requête minuscule |
| GHSA-86qp-5c8j-p5mr / CVE-2026-48710 | Host malformé et construction de `request.url.path` | 1.0.1 | Version affectée ; pas de contournement d’authentification démontré dans ce site |
| GHSA-jp82-jpqv-5vv3 / CVE-2026-54282 | Construction d’autorité/hostname par un chemin non validé | 1.3.0 | Version affectée ; exploitation spécifique non démontrée |
| GHSA-wqp7-x3pw-xc5r / CVE-2026-48818 | StaticFiles Windows, chemins UNC | 1.1.0 | Pas de chemin d’exploitation identifié pour le Worker Cloudflare, qui utilise le binding Assets ; attention au serveur FastAPI historique s’il est lancé séparément sous Windows |
| GHSA-x746-7m8f-x49c / CVE-2026-48817 | Dispatch `HTTPEndpoint` par méthode arbitraire | 1.1.0 | Le code audité emploie des routes FastAPI ; chemin d’exploitation non identifié |

La preuve locale vérifie que trois champs sont acceptés malgré `max_fields=1`, sans charger le service ni envoyer un gros corps. Elle ne constitue pas une attaque DoS sur le serveur en ligne.

**À faire avant publication :** choisir un couple FastAPI/Starlette compatible avec les versions corrigées, mettre à jour le verrou et rejouer les tests/compilation Worker. Ne pas forcer une mise à jour majeure à l’aveugle : les contraintes actuelles excluent les correctifs cités. Ajouter une borne globale sur le corps des requêtes, appliquée avant le parsing et contrôlant les octets réellement reçus, pas seulement Content-Length. Les limites de champs seules ne remplacent pas cette protection.

Sources : [avis parseur du mainteneur](https://github.com/Kludex/starlette/security/advisories/GHSA-82w8-qh3p-5jfq), [avis Host](https://github.com/Kludex/starlette/security/advisories/GHSA-86qp-5c8j-p5mr), [avis chemin](https://github.com/Kludex/starlette/security/advisories/GHSA-jp82-jpqv-5vv3). Données de requête de dépendances : `dependances_osv.json`. Les alertes ne prouvent pas toutes une exploitation effective de cette application.

### A01 — Élevé pour le secret du vote : rapprochement des générations et votes par instantanés

Preuves : `email_access.py:178`–`186` crée une délivrance liée au pseudonyme de l’adresse et un code dans le même batch. `worker.py:689`–`704` crée un émargement et un bulletin dans un même batch. Le bulletin contient directement `choix_id`, donc le choix est lisible par D1.

La preuve locale procède sans modifier le programme de vote :

1. Observer les ensembles avant et après une génération isolée : un pseudonyme de mail et un nouvel identifiant de code apparaissent ensemble.
2. Observer les ensembles avant et après un vote isolé : un émargement portant ce code et un bulletin portant le choix apparaissent ensemble.
3. Recalculer le pseudonyme pour une adresse candidate avec la clé HMAC du serveur, ou utiliser une identité déjà connue de l’observateur, permet de nommer la personne.

**Accès nécessaires :** lecture de la base à plusieurs instants ; pour transformer un pseudonyme en adresse candidate, accès à AG_CODE_KEY ou information d’identité externe. Ce n’est pas une attaque accessible à un simple visiteur anonyme. Deux lectures encadrant plusieurs votes peuvent laisser une ambiguïté ; la preuve montre qu’il existe néanmoins des cas identifiables, notamment un scrutin peu actif. Un administrateur serveur peut aussi instrumenter directement le trafic sans cette méthode.

Séparer les colonnes, supprimer les heures et utiliser des identifiants aléatoires ne bloque pas ce scénario. Les sauvegardes historiques peuvent également faciliter certains rapprochements. D1 dispose de Time Travel, mais la granularité documentée à la minute ne permet pas de supposer une observation de chaque transaction : ne pas présenter le test SQLite comme une extraction de l’historique D1 réel. [Documentation D1](https://developers.cloudflare.com/d1/reference/time-travel/).

**À faire :** si la menace inclut les administrateurs techniques, utiliser une architecture de scrutin auditée avec séparation effective des autorités, justificatifs non corrélables et protection des bulletins/chiffrement et dépouillement adaptés. Un simple correctif de suppression de mail ou une clé supplémentaire ne suffit pas. À court terme, retirer les accès D1 superflus, séparer le gestionnaire de la messagerie des opérateurs serveur, limiter les requêtes manuelles pendant le scrutin et ne pas promettre l’anonymat absolu. Ces mesures réduisent le risque sans constituer une preuve cryptographique.

### A02 — Élevé selon contexte : résultat individuel par clôture précoce ou petit effectif

Preuves : `worker.py:659` et `1035` révèlent les totaux à la clôture ; `worker.py:1081` autorise le créateur/principal à fermer sans quorum. `templates/ag_vote.html` affiche les nombres exacts, y compris « 1 voix ».

Test : un vote unique pour une option, puis clôture par le principal, rend immédiatement son choix déductible si l’organisateur sait qui est cette unique personne. Aucun accès D1 n’est nécessaire. Avec deux électeurs, l’un peut aussi soustraire son propre vote ; les résultats unanimes ou de très petits groupes ont des limites naturelles de confidentialité.

**À faire :** définir les règles de publication et de clôture avant l’AG, limiter les résultats détaillés sur petits effectifs selon une politique justifiée, prévoir plusieurs responsables pour les opérations sensibles et expliquer les limites des résultats agrégés. Ne pas inventer un seuil universel qui garantirait à lui seul l’anonymat.

### A03 — Moyen/élevé selon sujets : même pseudonyme entre toutes les AG

Preuve : `email_access.py:75` calcule l’empreinte de l’adresse sans inclure l’AG ; la même valeur sert aussi au compteur de demandes (`:98`). Le test obtient le même `email_hash` pour une adresse vérifiée dans deux AG.

Un lecteur de la base peut donc relier les délivrances de code entre assemblées, sans connaître le mail. Un détenteur de la clé peut tester une liste d’adresses universitaires candidates. Cela révèle une activité de délivrance/inscription, pas automatiquement un vote effectif ni son contenu.

**À faire :** employer un pseudonyme distinct par AG et par finalité, avec séparation de clé ou de domaine, et une portée anti-abus distincte, de durée courte. Prévoir une migration conservant l’anti-doublon existant sans rouvrir arbitrairement des droits. Cela réduit le profilage mais ne corrige pas A01.

### I01 — Moyen/élevé selon le modèle de confiance : accès aux OTP = possibilité d’usurpation

Preuves : `email_access.py:144` et `165`. La preuve locale initie une demande dans la session de l’attaquant pour une adresse cible, puis utilise l’OTP accessible dans le relais simulé ; un code est délivré au demandeur.

Le cookie protège contre le simple réemploi d’un OTP volé dans une autre session. Il ne protège pas une personne qui peut initier sa propre demande ET lire l’OTP envoyé à la cible. Un lecteur de la boîte universitaire, un relais compromis ou un opérateur ayant accès au contenu des OTP peut être dans ce cas. La simple connaissance de l’adresse seule ne suffit pas.

**À faire :** décider si ce niveau de confiance convient à une consultation informelle ; sinon authentification institutionnelle avec identifiant stable et assurance adaptée, sous réserve des accords nécessaires. Séparer les droits du relais et ceux du vote ; MFA sur les comptes de gestion. C’est un risque d’authentification/intégrité, pas la preuve qu’un code d’AG est encore envoyé par mail.

### I02 — Moyen : une adresse n’est pas nécessairement une personne

Le test peut créer deux codes avec deux adresses distinctes pour la même AG. L’acceptation de deux adresses différentes est voulue par le modèle actuel, mais ne garantit pas une personne/une voix. Le site accepte aussi la syntaxe avec `+` ; la distribution réelle d’alias par Sorbonne Université n’a pas été vérifiée.

**À faire :** pour des résultats ayant une portée représentative, définir une liste électorale ou un identifiant institutionnel unique. Si ce n’est pas possible, annoncer exactement « un code par adresse vérifiée », pas une unicité de personne prouvée. Ne pas supprimer mécaniquement les parties `+` ou points sans connaître les règles réelles du fournisseur.

### D01 — Moyen, impact important sur un campus : blocage au sixième demandeur derrière une IP

Preuve : `email_access.py:95`–`108` impose cinq demandes en quinze minutes par IP, en plus de l’adresse. Le test présente six adresses universitaires différentes depuis une seule IP : la sixième reçoit 429. Un campus, une résidence ou une salle peuvent partager une même IP publique.

**À faire :** distinguer les quotas par adresse, session et IP ; dimensionner la limite IP pour une vraie AG et surveiller les abus. Une limitation plus élevée doit garder une protection contre le spam et l’épuisement des quotas Gmail. La limitation actuelle peut aussi permettre de gêner une adresse connue en déclenchant ses demandes.

### D02 — Élevé pour la disponibilité de certaines opérations D1 : motifs SQL trop longs

Preuve : les quatre motifs GLOB de `migrations/004_durcissement.sql` font **76 octets**. D1 documente un maximum de **50 octets** par motif LIKE/GLOB. Le test reproduit l’erreur SQLite en appliquant cette limite. L’aperçu privé remplace précisément ces motifs (`.apercu_local/lancer.py:56`) : son succès masque donc cette différence avec le schéma de production.

**À faire avant publication :** examiner les triggers effectivement installés sur D1 et ajouter une nouvelle migration de correction des triggers, avec validation de dates compatible D1. Ne pas simplement modifier puis rejouer une ancienne migration 004 déjà appliquée. Tester la création et la modification d’un sujet dans une base D1 isolée avec exactement les migrations de production, sans réécriture locale. Les migrations 005/006 seules ne corrigent pas ce point.

Source : [limites D1](https://developers.cloudflare.com/d1/platform/limits/). Le schéma distant n’a pas été inspecté : l’impact sur une instance existante dépend des triggers qui y sont présents.

### O01 — Moyen : défense du compte administrateur à renforcer

Le code exige un mot de passe et utilise des empreintes PBKDF2, mais pas de second facteur applicatif. La limite de connexion est par IP (`worker.py:433`) et est vérifiée séparément de son incrément. Elle n’est pas une barrière complète contre les tentatives concurrentes ou distribuées. Le coût PBKDF2 factice pour un identifiant absent est de 100 000 itérations, contre 600 000 pour un compte récent : une différence de temps peut aider l’énumération, sans compromission de mot de passe démontrée.

**À faire :** MFA sur Cloudflare, Google et GitHub ; protection additionnelle des routes admin (Access ou mécanisme équivalent à configurer et tester), mots de passe uniques et limitation adaptée. Un contrôle d’accès déduit uniquement d’un en-tête utilisateur ne suffit pas. Le mot de passe de production réutilisé en aperçu augmente l’impact d’une fuite du poste ; l’utilisateur a demandé cette réutilisation, elle n’a pas été changée pendant l’audit.

## Points positifs observés

SQL paramétré ; auto-échappement Jinja ; CSP interdisant les scripts ; cookies Secure/HttpOnly/SameSite et signatures HMAC ; vérification d’origine et jetons CSRF ; contrôle créateur/principal ; non-double-vote et délivrance unique dans un batch ; vérification de l’AG et de l’option en SQL ; résultats masqués avant clôture dans les routes publiques/applicatives ; renouvellement de session après modification de mot de passe via auth_version.

Le relais accepte uniquement des OTP de six chiffres et des domaines exacts, vérifie une signature et une fenêtre temporelle, et n’est plus appelé à la génération du code d’AG. La migration 006 retire l’adresse en clair de la table active. Ces points ne suppriment pas les risques démontrés et ne certifient pas l’infrastructure.

## Données personnelles et secrets dans Git

Le `.gitignore` de cette copie finale a été renforcé et testé sur 34 chemins fictifs : 23 fichiers privés exclus, 11 fichiers publics conservés. Il exclut notamment `.env` et ses variantes réelles, `.dev.vars`, identifiants, clés privées, bases et journaux SQLite, mails, captures HAR, exports, sauvegardes, archives de livraison et l’aperçu privé. Les exemples vides peuvent être suivis ; ils doivent eux aussi être relus. Les migrations SQL, `uv.lock` et la configuration Wrangler de production restent versionnables.

**Ne pas ignorer globalement `*.sql`, `*.json`, `wrangler.jsonc` ou les fichiers de verrou : cela cacherait des éléments nécessaires au déploiement.** L’identifiant D1 et le nom du Worker ne sont pas des mots de passe. Les valeurs de secrets doivent rester dans les secrets Cloudflare/les propriétés privées du relais.

Dans le véritable dépôt Git, vérifier avant commit :

```powershell
git status --short
git diff --cached --stat
git diff --cached
git ls-files -ci --exclude-standard
git check-ignore -v .env cloudflare/.dev.vars .apercu_local/.state/acces_admin.txt
```

`git diff --cached` peut afficher des secrets s’ils ont été ajoutés : examiner localement, ne pas coller cette sortie dans une conversation. Si un fichier sensible est déjà suivi, `.gitignore` ne l’enlève pas. Après vérification du chemin, `git rm --cached -- chemin` retire seulement son suivi courant, pas son historique. La révocation/rotation du secret est prioritaire ; une purge d’historique éventuelle doit être coordonnée, pas lancée automatiquement. [Git](https://git-scm.com/docs/gitignore), [GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).

La recherche locale a inspecté **126 objets de fichier accessibles**, sans correspondance exacte avec les valeurs des secrets actuels connues de l’audit ; `.env` et les fichiers d’identifiants/base recherchés n’apparaissaient pas dans les chemins d’historique ciblés. Cela ne prouve pas l’absence d’un ancien secret différent, d’une copie distante ou d’une fuite hors Git. Ne pas publier tout le dossier parent Site_vote avec ses anciennes copies et données ; utiliser la racine exacte du dépôt.

Le mot de passe Gmail d’application apparu plus tôt dans une capture doit être révoqué s’il ne l’a pas déjà été. Le `.env` est dans un chemin OneDrive : vérifier sa synchronisation et les droits des sauvegardes. `.gitignore` ne protège ni OneDrive, ni une capture d’écran, ni un mail, ni les métadonnées auteur/email des commits. Examiner également l’identité Git publique et utiliser une adresse noreply si souhaité. Ajouter une détection de secrets côté GitHub/pré-commit avec un outil maintenu ; ne pas considérer les motifs d’exclusion comme un détecteur de contenu.

## Plan d’action

1. **Avant toute publication :** traiter S01 et D02 ; vérifier les secrets déjà exposés et les comptes de gestion ; arrêter la promesse d’anonymat garanti.
2. **Avant consultation réelle :** décider du modèle de confiance acceptable pour A01/A02 ; isoler les accès serveur/mail et corriger le pseudonyme inter-AG et les limites d’IP ; documenter le responsable, l’information, les contrats et la conservation.
3. **Si un secret fort vis-à-vis des administrateurs est requis :** choisir/faire auditer une architecture de vote adaptée plutôt que présenter cette séparation de tables comme suffisante.
4. Refaire les tests de sécurité, les tests métier et une validation de migrations sur D1 isolée ; vérifier les réglages réels avant de conclure à la préparation opérationnelle.
